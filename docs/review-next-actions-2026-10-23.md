## 1. 角度一：契约 / 合规

### C-1（必修）三件套技术文档不能是索引页

赛题 §五「作品资料」第 2 条原文：

> **技术文档**：系统架构图、核心算法说明、安全设计文档。

原计划 D5 写的是"三件套技术文档改为**索引页**（architecture / algorithms / security-design），指向已有 docs 七篇"，理由是"不新写 2 人日"。

这在契约上不成立：索引页是导航，不是"架构图 / 算法说明 / 安全设计"本体。
合规报告的估算是"素材现成（技术方案 §3.1 mermaid 直出、§5/§8 + docs 六篇归并）"，
即**内容早就写完了，缺的是"按赛题口径重排成三份"**，不是"从零写两万字"。

**修订**：三份各 1–2 页正文 + 架构图（mermaid）+ 指向 `docs/` 的深链，合计 1 人日，不是 0 人日。

### C-2（必修）GitHub 仓库地址 ≠ 仓库已建

赛题 §五.4 要"源代码，含 README、GitHub 仓库地址、部署说明、测试用例"。

实测：`git remote -v` 已有 `origin → github.com/YYYPROBEE/bah-monorepo`，但 `AGENTS.md` 门禁章节自述
"**本仓库为私有仓**，GitHub Free 不支持分支保护"。私有仓的地址评委打不开。

公开化的敏感面实测（这一步必须做，不能凭感觉）：

| 检查 | 结果 |
|---|---|
| `git ls-files sessions` | **0**（`.gitignore` 第 7 行挡掉） |
| `git ls-files coverage*` | **0**（第 8–9 行挡掉） |
| `.env* / .pem / .key / secret` | 仅 `packages/persistence/src/credentials/`（代码，非凭据） |

**结论**：公开化的数据风险低，但**动作必须排进日程**（D10，与终检同批），且要复核
`docs/` 里有没有内网路径、真实姓名、评审内稿。

### C-3（必修）DAG 规划缺口必须写进自评，不能漏

赛题 §3.3 三条：模糊表达识别 / **复杂任务拆解为有序子任务 DAG** / 中断回退与人工接管。
合规报告 R7 记的是"`runtime/src/{plan,goal,todo,scope}` 全占位"，风险等级"中"。

原计划全文没提这条。这不是"补不补"的问题——**不写进安全自评，就是隐瞒缺口**；
评委一旦按赛题条目逐条对，缺一条比"写了但没做"更致命。

**修订**：进 `security-self-assessment.md` 的已知风险表，口径「复杂任务当前走单轮工具链，
DAG 规划是显式未实现项，接口占位已在 `packages/runtime/src/plan`」。不补代码。

### C-4（应修）阈值语义：改一个数不够

赛题分级线（§3.1 表格）：黄色 = 日累计 **≤ 1000 元**；红色 = 日累计 **> 1000 元**。

实测判定链：

```text
DEFAULT_BANK_TOOLS.dailyTransferLimit = 5_000        // 元（bank-tools.ts:88）
        ↓ yuanToCents()
TierConfig.dailyTransferLimitCents = 500_000         // 分
        ↓ escalateTransferTier()（tier.ts:121-128）
limit = min(preview.dailyLimitCents, dailyLimitCents)
overLimit = dailyUsed + amount > limit  → 红 + reason='daily-limit'
```

改 `5_000 → 1_000` 后，1500 元的转账会正确升红。**但**：

`preview.dailyLimitCents` 来自 core 账本的**卡日限额 500_000**（`mock.test.ts:122` 断言），
`preview.remainingCents = 卡限额 − 已用`。于是用户看到"今日还可转 5000 元"，
转 1200 元却弹红级强验证 —— 展示口径和判决口径不是同一个数。

**修订**：改 Config 同时，把 mock 卡日限额一并降到 1000 元（或让 preview 也取 min）。
成本 0.5d（3 处配置 + 2 处测试 + 1 处快照），不是 0.25d。

### C-5（确认成立）砍 P1-2 卡片挂失是对的

赛题要求"至少覆盖 3 个核心场景（鼓励全覆盖）"。实测已有 4 个：
转账、账单分析、理财申购、余额/流水。缺卡片管理、订阅。

`至少 3 个` 已达标 → 砍 1.5 人日的卡片挂失是**失分不减分项**，成立。但要在自评里列"未覆盖场景"。

### C-6（确认成立）砍 HP-2 有据

处置方案 §4.3 原文："如果 RAG 不在主演示路径内，这件降级为 P2，先做 HP-0/HP-1。"
主演示线是转账（能力平面 §9 选 A 线），RAG 是知识问答侧线。依据成立。

但**注意**：自评里不能写"知识库有签名验签"，只能写"ACL + 时效窗 + 引用/数值校验"。
多写一句就是虚假陈述。

### C-7（新增）赛程里有一个免费的机会

赛题时间线：**10-28 线上答疑**。原计划没排。

不必占用工期，但值得把"评估口径 / 评审关注点"的两个问题提前写好，10-28 提。
成本 0.1d，收益是可能纠正一个方向性误解。

## 2. 角度二：工程正确性

### E-1（应修）`tracked-sources` 会自愈

`scripts/verify-tracked-sources.ts` 的判据第 1 条：

> `git ls-files --others --exclude-standard` 命中扫描面内的源码 → 失败

即：**只要有未跟踪源码就红**。`packages/eval`、`packages/memory-store`、`saga-bridge.ts` 一入库，该项自绿。
原计划把它列成"要修的一项"，是误判。真正要动手的只有两项。

### E-2（必修）`snapshot-fresh` 是"重录"，不是"修脚本"

判据（`verify-snapshot-fresh.ts` 头注释第 4–5 条）：

> 敏感面：runtime/llm/bank/saga/persistence/safety 的 `src/` + host 的 `boot/`；
> 场景归属：`snapshots/<case>/scenario.json` 的 `coveredSources` 必须覆盖敏感文件，且该 case 本次有改动。

`packages/host/src/boot/plugins/saga-bridge.ts` 落在 `host/boot/` → 属敏感面。
所以它不是"脚本报错"，是"新接线的插件没有对应场景覆盖"。两条路：

1. 把 `bank:saga-bridge` 行纳入 `snapshots/web-channel`（或新建场景）的 `coveredSources`，重录；
2. 证明该插件不进快照（不成立——它改的是装配行）。

审计 README 已经点过："快照 rows 不含 `bank:saga-bridge`，回放的是旧配置"——这正是红的成因。
重录后快照数据会**真的变**，必须逐 diff 复核，不能"看起来没变就过"。

### E-3（必修）D1 装不下，且顺序错了

原 D1：提交(0.5) + 修 3 红(0.5) + 阈值(0.25) + HP-0 第一段(0.5) ≈ **1.75d**。

实测修正后：提交 0.25 + 场景重录 0.5 + `verify-saga-wiring` 0.25 + 阈值 0.5 = **1.5d**。
HP-0 第一段必须挪出 D1。

### E-4（应修）eval 出数字不是 0.5d

实测三个事实：

1. `packages/eval` **不在** `tsconfig.host.json`、`vitest.config.ts`、`package.json`（三处 grep 均无命中）；
2. 它的用例在 `packages/eval/tests/`，根 vitest include 不含 → `pnpm test` 跑不到；
3. 已有 `attachSeamBridge`（`adapters/seamBridge.ts`）可按 duck-type 挂真实事件源，方向对。

所以"跑一次现成场景出数字"实际是：写 host→port 适配 + 接入 tsconfig + 让根 vitest 覆盖 +
跑一次 episode + 出表。**1d**，不是 0.5d。且这一步的真正价值不是"出数字"，而是把 eval 从
"本地包"变成"CI 可见包"——否则 PPT 引用它的数字时无法自证。

### E-5（应修）数字口径会分裂

`pnpm test` 当前 150 文件 / 1345 用例（10-22 审计基线），eval 另有 14 文件 / 133 用例，
但**不在**同一次运行里。`facts.md` 若只写一个总数，就等着被问"你这个数怎么复现"。

**修订**：facts.md 必须分三行写——
`pnpm test`（主仓）/ `pnpm -F @bah/eval test`（评测包）/ `pnpm test:web`（前端），各带命令。

### E-6（优化）两次快照重录可以合并成一次

阈值改 `host/boot/plugins/bank-tools.ts`，HP-0 改 `host/boot/plugins/web.ts` + `safety/src`。
两者同属敏感面。若分两天做，要重录两次、复核两次 diff。

**修订**：D2 一起改完（阈值 + HP-0 的 safety 部分），D3 一次性重录 + 复核 + 跑 gate。

### E-7（登记）修订后零缓冲

重排后 10 天刚好用满，一天不能超。**唯一可牺牲项是 HP-1**：
交付物一旦超时，立刻砍 HP-1（保住 D4–D8 的五类资料），不要挪 PPT/视频的天数——
那是"交不交得上"的分界线。
