## 1. 四条线的依赖关系

```text
身份/租户模型 ──┬── 会话隔离（存储分区 + 审计主体）
                ├── 配额（每租户限额/并发）
                └── 密钥（每租户 KMS 引用）
                        │
渠道（IM 或桌面）────────┘（一个渠道先做，复用 channel 端口）

场景补齐 ── 与上面三条**无关**，可完全并行
实体槽位 ── 先决定"静态画像"还是"动态 provider"，再谈代码
```

**关键判断**：多租户**不是**渠道的前置，但**是**"对外开放多用户"的前置。
只做渠道不做租户 = 单用户多入口（可以接受，也是演示级最现实的一步）。

## 2. 四条线的范围与风险

### 2.1 多租户 / 真实身份（5–8 人日，**独立架构项目**）

| 子项 | 内容 | 风险 |
|---|---|---|
| 身份模型 | 主体（user / tenant / agent）、凭据、会话归属 | 与现有 `SessionIdentityStore` 的兼容面：它按 `sessionId` 绑身份，加租户就要加二级键 |
| 会话隔离 | `sessions/<tenant>/<session>/` 分区；`bah audit` 按租户范围扫 | 现有链 id 是 `<sessionId>`，改路径等于**旧证据不可寻址**——必须先做迁移脚本 |
| 配额 | 每租户日限额、并发 turn、工具调用数 | 现有日限额是**单进程内存态**（`DEFAULT_LIMITS`），多租户必须先落存储 |
| 审计主体 | 每条链记录 `tenantId` / `actorId` | 链格式变了就要重算所有历史链的根——**不可原地改** |
| 密钥 | 每租户 KMS/HSM 引用 | 现在是文件私钥（`keys/`，gitignore）；KMS 是外部依赖 |

**结论**：这是 5 天起步、且**会动审计链格式**的项目。赛前做必翻车。

### 2.2 渠道（IM 或桌面，3–5 人日/个）

- **先选一个**，不要两个都做。推荐 IM 网关：它逼出"异步、多会话、无 UI"三件事，复用 `channel` 端口即可，不用打包 Electron。
- 复用面：`@bah/channels` 的 adapter 接口（`inbound` / `decide` / `attachApproval`）。Web 的 53 例行为基线可以直接平移成 IM 的用例骨架。
- 主要风险：**审批在 IM 里怎么点**。Web 有弹窗，IM 只有消息卡片 + 回调——需要一条新的"卡片动作 → `adapter.decide`"通路，且必须保留 CSRF 之外的等价防伪（回调签名）。
- 桌面端次要：`apps/desktop` 只是"打包 Web + 私有 host"，收益低于成本。

### 2.3 场景补齐（每个动作 0.5–1 人日，**可无限拆**）

按"每个动作都要过三级治理"的口径，下面的顺序按**复用度**排（先做能复用现有票据/判决的）：

| 优先 | 动作 | 复用面 | 新增风险 |
|---|---|---|---|
| 1 | 卡片解挂 / 额度调整 | 挂失的票据 + 黄级判决 | 额度调整是**写金额**，要过金额校验与日限额 |
| 2 | 理财赎回 | 申购的持仓与估值 | 赎回有"持有期费率"，必须走 `analysis_calc` 同一套受限计算，不能自己算 |
| 3 | 订阅识别 / 提醒 | `txn_query` 的分类 | 识别是**推断**，不能当事实写进账本 |
| 4 | 转账定时 / AA | 转账试算 | 定时 = 后台 job，需要 tick 框架（saga 有，bank 没有）。**2026-10-31 已落地**：定时走 `transfer_schedule`；AA 的 `collect` 于 2026-11-01 补齐（ADR-0011，模拟代收） |
| 5 | 风险评估问卷 | 无 | 属于合规流程，不是工具调用 |

红线：**每个新动作都必须有 tier、amountPath、审计事件**，否则 `verify-tiers` 会红——这是好事，它挡住了"随手加个工具"。

### 2.4 实体槽位（0.5 人日决策 + 1–2 人日实现）

现状是静态配置（`runtimeContext.user` / `notes`）。两条路：

- **A. 明确"静态画像"**（推荐）：把 `runtimeContext` 的注释改成"演示用静态画像，不接动态 provider"，
  并删掉代码里"将来会有 provider"的死分支（如果有）。成本 0.5 人日，收益是**口径不再含糊**。
- **B. 接动态 provider**：账户/流水从真实核心读。需要先有"数据源"这个服务键 + 失败降级策略；
  风险是**把仿真账本和真实账本混在一个会话里**，金额口径会出现两套。

## 3. 建议顺序（按"投入产出 / 风险"）

| 阶段 | 做什么 | 人日 | 为什么这个顺序 |
|---|---|---:|---|
| 0（现在） | 2.4-A 口径收口 + 本文件 | 0.5 | 零风险，先让"没做"变成明确的话 |
| 1 | 场景补齐 1–2（解挂、赎回） | 1–2 | 纯加法，不动架构；直接提升"业务纵深"这一项的观感 |
| 2 | 一个渠道（IM 优先） | 3–5 | 逼出真正的异步/回调设计，但不碰审计格式 |
| 3 | 实体槽位 B 或场景 3–5 | 1–3 | 看评分口径取舍 |
| 4 | 多租户 | 5–8 | 唯一会动审计链格式的项，必须单独排期 + 迁移脚本 + 全量重放验证 |

## 4. 赛前明确不做（写了就不再讨论）

- 多租户 / 真实登录 / 每租户配额；
- IM + 桌面**两个都做**；
- K8s / 多副本 / 分布式限流（与单机演示定位冲突）；
- 真实人脸 / 短信 / U 盾供应商接入（合规与外部服务）；
- microVM / Kata / Firecracker（Windows 无 KVM，换宿主风险高于收益）。

## 5. 这份路线图怎么被证伪

每阶段结束时用可执行的判据收口，而不是"感觉做完了"：

| 阶段 | 判据 |
|---|---|
| 0 | `grep -rn "静态画像" docs/` 有命中；profile 注释与本文一致 |
| 1 | 新工具在 `verify-tiers`（tier + amountPath）与 `docs/tool-catalog.md` 里都有；16 → 18 |
| 2 | 一条 IM 消息能完成"查余额 → 转账 → 审批 → 结果"；回调签名有负例 |
| 3 | 动态 provider 断开时，会话降级为"画像不可用"而不是编造数据 |
| 4 | 两个租户的会话目录、审计链、配额互不可见；旧链迁移脚本留下前后根哈希对照 |
